# 1. 采用 G-CAT 项目治理标准

- **状态**：已接受
- **日期**：2026-09-24
- **决策者**：G-CAT（用户）+ 诺亚（AI 管家）

## 背景（Context）

仓库历经 v6/v7 多次大迭代，暴露出系统性问题：

1. **接手成本高**：新会话（人或 AI）不知道项目是干什么的、做到哪一步、下一步往哪走；每次都要靠翻代码和聊天记录考古。
2. **能力无真相**：系统实际有什么能力、哪些改了、哪些废弃了，只能读代码反推；README 声称的部分与实际不符（如 RRF 只在 wiki 实现、主搜索是线性加权）。
3. **只增不减**：功能叠加缺少「废弃」表达，死代码与历史遗留累积。
4. **规范缺失**：`AGENTS.md` 达 8,466 字符（每个请求都加载，且超出 Hermes 20,000 字符上限的合理区间）；无 CHANGELOG 治理、无决策记录、无规格层。
5. **各仓库做法不一**：同类问题反复踩（版本号漂移、tag 缺失、`.gitignore` 漏敏感文件）。

## 决策（Decision）

采用 **G-CAT 项目治理标准 v1.0**（`~/gcat-std/STANDARD.md`），本仓库按 **L 档**执行：

- **宪章层**：`PROJECT.md`（这是什么/为什么/去哪）+ `AGENTS.md`（**瘦身至 ≤30–60 行**）+ `CHANGELOG.md` + `README.md`
- **规格层**：`openspec/specs/`（能力真相）+ `openspec/changes/`（变更提案，含 ADDED/MODIFIED/**REMOVED**）+ `docs/adr/`（决策记录）
- **流程层**：Spec → Plan → Tasks → Implement → **Validate**
- **门禁层**：CI 三件套（test / version-scan / privacy-audit）+ `repo-doctor` 巡检 + 四段式发布门禁

对标：Linux Foundation **AGENTS.md** 标准（2025-12 归入 Agentic AI Foundation）、2026 主流 **Spec-Driven Development**（OpenSpec / GitHub Spec Kit）。

## 后果（Consequences）

- ✅ **接手 3 分钟**：读 `PROJECT.md` → `AGENTS.md` → `openspec/changes/` 即掌握全貌
- ✅ **能力有真相**：`specs/` 是唯一权威，不再靠读代码反推
- ✅ **防大乱炖**：`REMOVED Requirements` 强制为废弃能力留名，三个月后不会有人再把它加回来
- ✅ **决策可追溯**：每条架构取舍落 ADR，不再只活在聊天记录里
- ✅ **token 成本下降**：AGENTS.md 每次请求的注入量减少约 74%
- ⚠️ **代价**：每次改行为多写一个 `proposal.md`（轻量路径可三行）；需要养成收尾习惯
- 🔄 **放弃了**：「所有文档一处写完就算了」的做法；也放弃为存量代码补全量规格基线（按 brownfield 原则围绕真实改动长）

## 备选方案（Alternatives）

| 方案 | 为什么不选 |
|---|---|
| 维持现状（无治理层） | 已证明持续产生重复踩坑与考古成本 |
| 引入外部工具（OpenSpec CLI / Spec Kit） | 违背自建生态优先；且依赖外部 npm/pip 工具链，离线不可用。**结构照抄，工具自建** |
| 一次性补齐全量规格与文档 | 大而全的基线没人验证，从第一天开始腐烂（OpenSpec 官方立场亦如此） |
| 只做 AGENTS.md 瘦身 | 治标不治本：不解决「能力真相/决策记录/变更表达」三个根问题 |
