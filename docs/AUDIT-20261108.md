## 四、性能基线（生产实测，2026-11-08）

| 场景 | 延迟 |
|---|---|
| 纯关键词通道 | **77 ms** |
| 四通道（含语义）· 首问 | **512 ms**（embedding API 往返） |
| 四通道（含语义）· 同一问句复问 | **93–125 ms**（进程内缓存） |
| 10 并发召回（预发布） | p50 507ms / p95 509ms，全部 200 |

结论：慢在「第一次问一个新句子」，不是检索本身。真要优化就做**跨进程查询向量缓存**，属于优化不是修复。

## 五、仍然存在的边界（不粉饰）

1. **没有自动回滚**：回滚靠人执行 `cp -a .backup-<ts>/. .` 或 `git checkout`，没有一键脚本。
2. **staging 与生产共用密钥**：预发布会真调外部 API，产生少量费用。
3. **staging 数据是快照**：不含之后的生产增量，历史数据损坏类问题验不出来。
4. **同机部署**：共享 CPU/内存，压测结论不可靠。
5. **生产 git 里曾跟踪过 `.backup-*`**：历史里仍有旧备份对象，repo 体积偏大（可后续 filter 清理）。
6. **无独立告警**：备份失败有邮件节流通知，部署失败没有（靠人跑脚本看输出）。

## 我自己犯的两个方法错误（记下来防复发）

1. **用子串出现次数当命中数**：召回响应里回显了 query/keywords，我把回显也算成「命中」，
   于是「删后仍可见」「并发落 3 条」两个假失败。DB 实证：恰好 1 行、已删 1 行 ⇒ 产品是对的。
   **判据必须解析结构（candidates[].head），不能数整段 JSON 里的字符串。**
2. **参数名猜错**：`/exact` 要 `q`、`/keywords` 要 `keywords`，我传了 q/query/kws 三个混合体
   ⇒ 两个用户都返回 0 条，看着像「隔离成功」，实际是空跑。

## 评测尺子的盲区（重要）

修完 C/T 通道后，`recall@10` 仍是 **94%**（改前改后一样）——
因为 demo 评测集里全是「结果卡」，**覆盖不到占 89% 的非卡片记忆**。
⇒ 尺子只能证明「卡片检索没退化」，**证明不了「真实语料检索变好了」**。
下一步该造一批基于真实非卡片记忆的题（这是评测集的缺口，不是代码 bug）。
