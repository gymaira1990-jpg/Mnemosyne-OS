# 版本规划（2026-11-07 立）

> 主人原话：「你这边发版是不是发的太频繁了？规划好的一个阶段性的任务，完全跑完了，
> 我们两个确定没问题了再发。这个逻辑不对的，应该是我们先计划出一个版本来，
> 完成目标之后再发。」

## 为什么改

2026-11-07 一天发了 **9 个 patch**（9.0.20 → 9.0.28），每完成一段就 tag + Release。
后果：

| 问题 | 具体代价 |
|---|---|
| 仓库日志噪音 | release 列表变成「工作流水」，看不出哪里是里程碑 |
| 验证成本重复 | 每个 patch 都要跑一遍全量门禁 + 部署 + 回证（约 6–10 分钟） |
| 版本号失去意义 | 9.0.2x 这十个号之间没有「阶段性差别」 |
| 对外可读性差 | 别人看你一天九个版本，只会觉得没规划 |

## 新规矩（立即生效）

1. **一个阶段 = 一个版本。** 阶段目标先写死在下面这张表里，达标前**不发版**。
2. 阶段内的改动照常提交 `main`（保持随时可回滚），但**不打 tag、不发 Release**。
3. 阶段收尾需要三件齐：① 目标表全绿 ② 全量门禁（测试/ lint / prod-diff / CI）全绿
   ③ **主人确认**。三者齐了才 tag + Release 一次。
4. 阶段中途发现新问题 → 进「下一阶段候选」，不临时插进当前版本（防止范围蔓延）。
5. 生产部署不受此限：**代码可以先上生产验证，版本号后置**——部署是运维动作，发版是对外承诺。

### 第 7 项的真实结论（负面但值钱）

| 轮 | 判据 | 结果 | 人工核对 |
|---|---|---|---|
| 1 | 数字 + 语境重合 0.6 | 331 对 | 抽样误报 |
| 2 | + 连续公共子串 ≥ 4 | 5 对 | **5/5 假阳性**：「22KB 帧」vs「158KB 帧」是两个不同实验；「2.2G 僵尸」vs「1.53 GMV」毫不相干 |
| 3 | + **题名相似 ≥ 0.4**、只比摘要正文 | 1 对 | 仍是假阳性：v4 含 7 张图 / v6 含 8 张图，两个版本都对 |

⇒ **提炼型结果卡里，「同一说法两个数字」几乎不存在**（同一事实只会落一张卡）。
所以「前段 vs 回捞谁优先」这条规则**缺少真实样本，暂不立**——按「先有样本再定规则」办事，
省掉一条拍脑袋的规则。检测器保留（换语料可能有用），判据与假阳性样例已进测试。

⇒ 7/8/9 完成 + 主人确认 = 发 **9.0.29**（一次性）。

```bash
cd ~/mnemosyne-dev
make test && make lint && make prod-diff && make numbers-check
env -u PYTHONPATH hermes verify --json          # 记录证据
git tag -a v<版本> -m "<阶段名>"; git push origin main && git push origin v<版本>
gh release create v<版本> --notes-file <CHANGELOG 对应段>
```
