🛡 S1 可靠性 — 修真缺陷写得对 · 收得回

原子性写入原为三步 autocommit，崩溃会留"有主行、无实体、无分词"的半成品记忆。改为单事务包裹，任一步失败整体回滚。
幂等键崩溃重试 / 断线重发 / 重复提交，现在返回原 id 不再产生新行（部分唯一索引 + ON CONFLICT DO NOTHING，历史 NULL 行不回填）。
记忆回收原系统全仓无 DELETE、无 VACUUM —— 软删即终点。现补 tombstone → purged 环节，五道安全闸放行，默认干跑，可整批还原。
完整性巡检新增 jobs/scrub.py（只读）：6 类孤儿与异常 —— 孤儿 inode / 悬空信念证据 / 到期未回收 / 缺指纹 / 活子挂死父。
可观测写入/召回延迟埋点（p50/p95/p99，成本≈0）+ GET /api/v1/metrics 一屏看全。此前有 2000ms 阈值却全无埋点，阈值形同虚设。
备份复验原备份只回答"跑没跑"（曾静默失败 36 天）。现四验：新鲜度 / 体积 / 真读 pg_restore TOC / --deep 真恢复到临时库比对行数。

🔍 S2 检索质量 — 找得准先量后改

前置纪律改召回排序前必须先有评测基线 —— 红队原话："RRF 更好"无评测支撑则不采信。
四通道融合点名 / 引导 / 共鸣 / 文库 原为各自返回、不融合。现各取 50 候选 → RRF 排名融合(k=60) → 统一截断。只按排名融合 = 量纲无关（原做法把余弦距离/BM25/时间三种量纲直接相加）。
两个细节命名空间隔离：记忆与 Wiki 是两套 id 空间，融合前分别加 m:/w: 前缀，否则不相关条目互相加分；可解释：channels 字段回答"这条为什么排上来"。
零行为变化融合默认关闭（?fused=true 才启用）—— 评测数字出来之前，线上行为一行不改。

🗂 S3 治理 — 弄得清制度而非文档

分层可执行5 层记忆模型不是文档：classify_layer() 在写入路径上真跑，每条记忆落 metadata.layer；对外有 /api/v1/layers 与 self_check。
诚实标注约束层（L3）的载体在 Hermes 侧（SOUL / MEMORY / config），不在库内 —— 用断言锁住，防止被硬塞 category 假装存在。
发布状态机本地 → 真实环境 → 部署 → 公开 → 归纳，未过上一段不得进入下一段（越段被硬拒）。本版发布即第一个回填样本。
产出物指针交付=箱子 / 检索=Wiki / 版本=仓库；记忆里只放指针 + 指纹，不放实体。

⚠️ 发布途中真实事故 —— 教训保留本版最重要的收获

现象部署到生产后，第一发写入即 500。
there is no unique or exclusion constraint matching the ON CONFLICT specification
根因dedup_fingerprint_key 是部分唯一索引（带 WHERE 谓词），而写入写的是不带谓词的 ON CONFLICT。部分索引推断要求谓词显式匹配 —— 缺谓词直接报错，整条写入路径挂掉。
为什么单测没抓到已有测试只验证"索引能拦住重复指纹"（裸 INSERT），从没跑过产品代码里那条真实的 INSERT ... ON CONFLICT。
铁律测了索引 ≠ 测了使用索引的那条 SQL。凡"代码里拼出来的 SQL"与"库里建的对象"有耦合，就必须把真实 SQL 拉出来跑一遍 —— 现已改为从源码正则抽 SQL 投库执行的测试，删掉谓词立刻变红。

🔧 发布后修正 — 同一版本号内吃掉测试阶段的账不带到下个版本

僵尸记忆GC 整批还原原只归档主表与轨迹，被级联删掉的实体 / 关键词 / 著录卡回不来 —— 修成四表全快照 + 还原完整性断言（撤掉修复测试立刻红）。
幂等键误杀内容指纹与"允许矛盾"的日志层自相矛盾，会误杀合法日志 —— 改为指纹分层（日志层按来源上下文与小时桶，其余按内容）。
半修上面第二处在生产环境实测才暴露 —— 本地单测抓不到，因为"只测了纯函数，没测整条写入路径"。
